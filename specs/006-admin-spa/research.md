# Research: Schema-Driven Admin SPA (Slice 6)

**Date**: 2026-11-05 | **Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

All findings below are grounded in the actual repo (`apps/api/src`, `packages/*`) as of this date — not in the spec's assumptions. Where the spec and the API disagree, the API wins and the client adapts (no API changes in this slice).

## R-01 — Better Auth client in a static-export SPA

- **Decision**: Use the `better-auth/client` framework-agnostic client (`createAuthClient` from `better-auth/client`) with `baseURL: NEXT_PUBLIC_API_URL`, plus `fetchOptions: { credentials: 'include' }` so the session cookie flows on the cross-origin `admin.<parent>` → `api.<parent>` calls. Auth state via the client's `useSession` hook (or a thin `auth.tsx` context wrapping `client.getSession()`); login via `client.signIn.email({ email, password })`; logout via `client.signOut()`. All admin API calls use the same `credentials: 'include'` fetch wrapper.
- **Rationale**: The server mounts vanilla Better Auth (`emailAndPassword`, cookie session, `trustedOrigins` from `CORS_ORIGINS`) at `/api/auth/*` (`apps/api/src/openapi.ts:10`, `packages/auth/src/auth.ts`). The framework-agnostic client works in any React SPA; no Next.js server integration is needed or allowed under static export. Cookie attrs (`Domain=.parent; SameSite=Lax; HttpOnly`, `Secure` in prod) already support the two-subdomain topology.
- **Alternatives considered**: Hand-rolled fetch to `/api/auth/sign-in/email` — rejected: reimplements cookie/CSRF edge cases the maintained client already handles. `better-auth/react` Next plugin — rejected: depends on server components/middleware, incompatible with `output: 'export'`.
- **Open verification (tasks phase)**: confirm the exact Better Auth version's client import path and whether mutations need an explicit CSRF/`origin` header when called cross-origin with `SameSite=Lax` (Lax permits top-level GET navigation; `fetch` POST from `admin.<parent>` to `api.<parent>` is same-site thanks to `Domain=.parent`, but verify against a live dev API in quickstart step 1).

## R-02 — Static-export-safe routing and data loading

- **Decision**: App Router with **no dynamic segments** — list/detail state travels in search params (`/content?contentType=<id>&doc=<docId>&locale=<fr>`, `/media?folder=<id>`, `/content-types?type=<id>`), read via `useSearchParams` inside `<Suspense>` boundaries. Every data view is a client component (`'use client'`) that fetches after mount and renders loading / error-with-retry / empty states. Navigation with `<Link>`; `trailingSlash: true` respected (link to `/content/`-style paths or rely on Next normalisation). No `generateStaticParams`, no server-side fetching anywhere.
- **Rationale**: `output: 'export'` + `trailingSlash: true` + `images.unoptimized` are already set in `apps/admin/next.config.ts`. Dynamic segments would force prerender-time params; search params keep the export a fixed set of HTML shells with deep-linkable UI state (spec Edge Case: "deep links work from the CDN"). Amplify SPA rewrites serve `index.html` fallback — 404s become client-side "not found" states, including the locale-missing case (R-07).
- **Alternatives considered**: Dynamic routes with `export` + `dynamicParams` — rejected: requires knowing all type/document ids at build time, contradicts "new field/type appears with no redeploy" (SC-004).

## R-03 — Schema-driven rendering from registry payloads

- **Decision**: Two generic renderers driven exclusively by `GET /api/v1/content-types` (list) and `GET /api/v1/content-types/:id` (returns `{ ...type, fields }`):
  - `SchemaTable`: columns derived from `fields[]` — display scalar-ish types (`text`, `email`, `uid`, `number`, `date`, `datetime`, `enumeration`) as text, `boolean` as yes/no, `media`/`relation`/`component`/`dynamiczone`/`richtext`/`markdown`/`json` as compact placeholders ("—" / count / thumbnail), plus fixed status/per-locale/updated columns from the document row. Never renders per-type branches; an unknown `fieldType` falls back to a JSON dump cell with a console warning (forward-compatible with future registry types).
  - `SchemaForm` + `FieldWidget`: widget map keyed by the 16 `VALID_FIELD_TYPES` (`packages/auth/src/fields.ts`): `text`/`email`/`uid`→text input, `richtext`/`markdown`→textarea (WYSIWYG explicitly out of scope), `number`→numeric input, `boolean`→checkbox, `date`/`datetime`/`time`→native pickers, `enumeration`→select from `validation.enum`/`validation.options` (verify key in tasks phase against a live registry row), `media`→MediaPicker button + thumbnail, `relation`→id/slug text input (rich autocomplete is a later slice), `component`/`dynamiczone`→nested sub-form/repeatable group (recursive `SchemaForm`), `json`→textarea with JSON validation. `required` ⇒ marker + `required` attr; `localized` ⇒ field participates in per-locale editing; reserved names (`id`, `createdAt`, …) are never rendered as inputs.
- **Rationale**: Satisfies FR-003/FR-004 and P-06/P-07 directly; the field-type universe is finite and enumerated server-side, so the widget map is closed but data-driven. Schema-version-mid-edit (spec edge case) is handled by re-fetching the type on save and comparing `activeSchemaVersion`, warning + revalidating on mismatch.
- **Alternatives considered**: Code-generating per-type components at build time — rejected: violates P-07 and breaks SC-004 (no-redeploy requirement).

## R-04 — Permission discovery for nav/action gating (no new endpoint)

- **Decision**: Resolve the caller's permission set client-side with **no new API endpoint**: (1) identity from the Better Auth session (`user.id`, `user.isSuperAdmin` — present on the session user via `additionalFields`); super-admins get the full nav. (2) Non-admins: `GET /api/v1/users/{userId}/roles` → for each role `GET /api/v1/roles/{roleId}/permissions` (both endpoints exist in `routes/rbac.ts`) → union of `resource.action` strings via the existing `GET /api/v1/permissions` catalogue. Cache for the session. (3) If any of those reads 403s for a low-privilege user, fall back to **progressive disclosure**: render Content + Media, hide admin sections, and hide/disable any control whose mutation returns 403 (cache the negative result for the session so it only flashes once). Server remains the enforcer in all cases.
- **Rationale**: The API has no "my permissions" endpoint and this slice adds no API routes. `resource.action` strings (`document.publish`, `media.manage`, `content-type.read`, …) are stable and documented in `packages/auth/src/rbac.ts` + `middleware.ts`. Progressive disclosure guarantees the Author-role acceptance scenario even if the role-read chain is locked down.
- **Alternatives considered**: New `GET /api/v1/me/permissions` endpoint — rejected for this slice (API change, needs its own spec/tasks; flagged as a Slice-7 candidate if the fallback proves janky). Pure try-and-hide on 403 with no prefetch — kept as the fallback, not the primary, because nav should settle on first paint, not after a failed click.
- **Verify in tasks phase**: that a non-admin session can read its own `users/{id}/roles` chain; if not, tasks must implement the fallback path first.

## R-05 — Document list has no server pagination (spec↔API gap)

- **Decision**: `listDocuments(contentTypeId, locale)` returns the **full unpaginated array** (`packages/auth/src/documents.ts:224`); `GET /documents` wraps it as `{ data }` with no `meta`. The admin therefore implements **client-side pagination** (default 25/page, page in local state, reset on filter/type change) over the fetched array. Documented as a known scale ceiling: acceptable for editorial scale (hundreds–low-thousands/collection); a server-paginated `GET /documents` is flagged as follow-up API work, not this slice.
- **Rationale**: Matches the verified code; the spec's "pagination matching the API's page/pageSize contract" describes the **media** list contract (`page`/`pageSize` ≤ 100, `{ data, meta: { page, pageSize } }` — `packages/storage/src/media-service.ts:151`), which the media grid uses server-side. Documents adapt client-side. No API change, no spec change needed beyond noting the asymmetry in `contracts/admin-api-client.md`.
- **Alternatives considered**: Adding `page`/`pageSize` to `GET /documents` — rejected: API change outside this slice's charter.

## R-06 — Validation errors are strings, not the `details[]` envelope (spec↔API gap)

- **Decision**: The implemented API returns validation failures as **string messages** (`Missing required field: <name>`, `Invalid type for field <name>: expected <type>`, slug `Conflict…` → 409, `res.status(400/422).json({ error: msg })` in `routes/documents.ts`), NOT the `{ error: { details: [{ path, message }] } }` envelope the spec's FR-004 assumes. The form's error mapper therefore: (1) regex-matches known message shapes to field paths (`/Missing required field: (\w+)/` → that field; `/field (\w+):/` → that field); (2) shows the raw message as a field error when matched, otherwise as a form-level banner; (3) always preserves payload on failure; (4) treats 409 slug conflicts as a slug-field error. Unknown shapes degrade to the banner — never silent.
- **Rationale**: Client adapts to the built API; the envelope upgrade (if desired) belongs to a future API slice with its own contract tests. The mapper is table-driven so swapping in real `details[]` parsing later is a one-function change.
- **Alternatives considered**: Changing the API to emit the envelope now — rejected: cross-slice API change with contract-test blast radius.

## R-07 — Locale-missing and session-expiry edge handling

- **Decision**: `GET /documents/:id?locale=<xx>` with no row for that locale: treat the resulting 404 (or empty) as the **"translation missing" empty state** (FR-005) — blank translatable fields + "untranslated" badge, never en-values. "Save" in that state issues create-with-locale through the normal create/update path. On **any** 401: stash the in-memory form draft (React state persists across the redirect guard where feasible), redirect to `/login?returnTo=<current>`, resume after re-auth. 403 on publish/force-delete ⇒ inline "not permitted" notice (never a crash). All error states render the envelope's `code`/`message` + `requestId` where present with a retry action.
- **Rationale**: Directly implements the spec edge cases with verified primitives (`getDocument(id, locale)` returns null → 404; middleware 401/403 shapes). No `requestId` field was found in current error bodies — the `ErrorState` component renders it **only when present**, and its absence is noted in the client contract rather than assumed.

## R-08 — Media signed-upload client sequence

- **Decision**: `UploadDropzone` implements the state machine `pre-check → sign → PUT → confirm → done/failed`: (1) client pre-check of MIME (SVG hard-rejected — server rejects even with the old env bypass, `media-svg.test.ts`) and size against configured limits; (2) `POST /media/sign { filename, mime, sizeBytes, folderId }` → `{ url, params }`; (3) direct `PUT` of raw bytes to `url` with `params` as multipart/form-data fields (Cloudinary-style unsigned/signed POST convention) using `XMLHttpRequest` (progress events — `fetch` lacks upload progress); (4) `POST /media { providerKey, mime, sizeBytes, folderId, alt, … }` to confirm; (5) errors mapped per FR-009 (`FILE_TOO_LARGE` names limit/received, `MIME_NOT_ALLOWED`, 413 ⇒ pointer to signed flow, `FOLDER_DEPTH_EXCEEDED`/`FOLDER_CYCLE`, `MEDIA_REFERENCED` 409 with `references[]` ⇒ blocking dialog + force path gated on `media.manage`). Thumbnails via `transformUrl` presets server-side pattern; admin uses plain `<img>` (unoptimized) with the provider URL.
- **Rationale**: Mirrors `StorageProvider.signUpload/confirmUpload` (`packages/storage/src/provider.ts`) and the route-level coded errors in `routes/media.ts`. XHR-for-progress is the standard exception to fetch-only code.

## T009 Verify-Live Results (2026-11-06, dev API on :3100, fresh `peggy_slice6` DB)

1. **CSRF/origin header on cookie mutations: NOT needed.** `POST /api/v1/content-types` with only the session cookie (no `Origin`, no CSRF header) passed auth — a non-privileged user got 403 (auth OK, permission denied), and after `is_super_admin=true` the same call returned 201. R-01 stands as designed.
2. **Roles chain for non-admins: partially open, key link missing.** `GET /api/v1/roles` → 200 and `GET /api/v1/permissions` → 200 for a fresh non-admin session, but **`GET /users/:id/roles` does not exist** (404 — only POST/DELETE assignment endpoints). So `myPermissions()` in `api-client.ts` correctly resolves to `null` today and the **R-04 progressive-disclosure fallback is the operative path**, not a fallback: nav shows Content + Media for non-super-admins, hides admin sections, and caches 403s per session. A future `GET /users/:id/roles` + `GET /roles/:roleId/permissions` endpoint pair remains a Slice-7 candidate.
3. **Enumeration options key: `validation.options`.** A live `enumeration` field round-tripped as `"validation":{"options":["draft","review"]}` — the form's enum widget must read `validation.options` (also accept `validation.enum` defensively). Recorded for T016.
4. **Folder CRUD permission: `media.manage` on writes, open reads.** `POST /media-folders` as super-admin → 201; `GET /media-folders` with session → 200. Matches the contract table.

> Also verified: session user payload carries `isSuperAdmin`/`isActive`; `signUp.email` sets `better-auth.session_token` with `Domain=.parent` (curl needs explicit `Cookie:` header against localhost; browsers on `admin.<parent>` are unaffected).
