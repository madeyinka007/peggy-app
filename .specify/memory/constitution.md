# Peggy CMS Constitution

## Core Principles

### I. Modular Monolith Boundaries (NON-NEGOTIABLE)

Peggy is a modular monolith: one deployable API (`apps/api`, Express + `serverless-http`), one static admin SPA (`apps/admin`, Next.js export), one Postgres database, Cloudinary for binary media. All content behavior derives from a versioned Schema Registry. All reads and writes flow through the Document Service and Query Engine. No layer bypasses another.

Non-negotiable import boundaries, enforced by lint and arch tests (build fails on violation):

- **P-01 API never touches the DB.** Controllers take services via dependency injection; they never import or call `db` directly.
- **P-02 Domain never imports Express, Drizzle, Next.js, Cloudinary, or Better Auth.** Domain code is pure and framework-agnostic.
- **P-03 Core never imports the Cloudinary SDK.** Core depends only on the `StorageProvider` port.
- **P-04 Core never imports Next.js.** The admin SPA is a pure API consumer.

Rationale: these boundaries keep the domain testable, keep the API portable across runtimes (local listen, Lambda handler, CI), and prevent infrastructure leakage into business logic.

### II. Metadata vs Content Separation

Schema definitions are rows, never tables. Content payloads are immutable JSONB versions, never columns-per-field.

- System metadata (users, roles, permissions, content types, fields, components, locales, media, API tokens, webhooks, audit, outbox) is relational, migrated, and strongly consistent.
- Content payloads live in `documents` (identity) + `document_locales` (pointers) + `document_versions` (immutable `data JSONB`) + `document_relations` (edges). No per-content-type DDL in MVP (D1).
- Queryability comes from GIN indexes on `data` plus extracted columns and partial indexes — never from new tables per content type.

Rationale: a single stable schema supports arbitrary content models defined at runtime without migrations or downtime.

### III. No Polymorphic Foreign Keys / No In-Request DDL

- **DB-02:** No polymorphic foreign keys (`reference_id + reference_type`). Every association is an explicit edge table or a nullable FK.
- **DB-03:** No in-request DDL. Content schema changes are data rows in the registry, not `ALTER TABLE`. Migrations run as a blocking CI job before traffic reaches a new revision — never inside handler boot.
- Every content write is one transaction touching `documents + document_locales + document_versions + document_relations + audit_logs + outbox`.

Rationale: polymorphic FKs defeat referential integrity; in-request DDL breaks serverless cold-start budgets and transactional consistency.

### IV. Auth Port Boundary

Human authentication uses Better Auth, kept behind the `AuthPort` interface so domain code never imports Better Auth directly.

- Password hashing: Better Auth scrypt default for MVP (OWASP-acceptable, zero deps). Argon2id is a documented post-MVP upgrade via custom `hash`/`verify` with a dual-verify transition window.
- Peggy's `users` table IS Better Auth's `user` table, extended via `additionalFields` (`displayName`, `avatarAssetId`, `isActive`, `isSuperAdmin`).
- Peggy's `sessions` table IS Better Auth's `session` table plus `revokedAt` (explicit logout tombstone).
- ID interop: `advanced.database.generateId = false` so Postgres generates UUIDs; `user.id` is `uuid` (Peggy UUIDv7), `session/account/verification.id` are `text`, `userId` FKs are `uuid`.
- The Better Auth organization plugin is NOT installed in MVP (D2 single project). Multi-tenant adoption is a future minor-version migration; no `tenant_id` columns in MVP.
- Session lifetimes: 7-day expiry, 24h update age, 5-min JWE cookie cache. Auth tables are generated by the Better Auth CLI and committed verbatim.

Rationale: the `AuthPort` boundary keeps auth swappable; Better Auth owns its tables so Peggy never hand-writes them.

### V. Single-Project-per-Deploy (D2)

One deploy equals one project. There is exactly one tenant per database. No `tenant_id` columns on any MVP table.

- The API artifact runs identically locally (`listen()`), on Lambda (handler), and in CI integration tests — adapter selected by environment, never by code fork.
- Lambda stays outside a VPC (Neon reached over the internet) to keep cold starts low.
- Provisioned concurrency is NOT budgeted in MVP; cookie cache + warm preview cover demo paths.

Rationale: multi-tenancy adds unused joins, admin surface, and migration weight for zero MVP benefit.

### VI. Security & Privacy Baseline (NON-NEGOTIABLE)

- Rate limiting follows the `lambda` preset: auth 5 req/min/IP, public 100 req/min/IP, publish 30 req/min/user. Counters live in Postgres (or future KV), never in process memory — brute-force protection must survive stateless scale-out.
- CORS allowlist contains only explicit Amplify origins; never `*` with credentials.
- Session cookie: `Domain=.parent; Secure; SameSite=Lax; HttpOnly`.
- CSRF tokens on cookie-session mutations; Bearer tokens (prefixed, hashed at rest) for programmatic/public API.
- Audit payloads redact credentials, tokens, and passwords at write time. Logs mask `*SECRET*`, `*KEY*`, `*TOKEN*`.
- The draft-leak fixture (public token × draft-only content → 0 rows) is a hard CI gate on every PR.
- Owner-only condition enforced in the permission evaluator; `createdBy` is immutable.

Rationale: security failures (draft leaks, credential exposure, brute force) are existential for a CMS; these rules are not polish.

### VII. Quality & Testing Gates

- Domain modules (publish machine, fallback resolver, permission evaluator, filter compiler) MUST maintain ≥80% branch coverage.
- OpenAPI snapshot (`/api/v1/openapi.json`) MUST cover 100% of routes; the generated TypeScript client MUST compile without `any`.
- Arch tests (domain ↛ infra/app; controllers ↛ db) and dependency-cruiser rules MUST pass in CI.
- The draft-leak fixture and owner-only matrix are required status checks on every PR.
- Schema changes are data rows — never DDL, never part of migrations.

Rationale: these gates catch regressions in the highest-risk paths (publish state machine, permission evaluation, public API scoping) before they reach production.

## Additional Constraints

**Technology stack (locked):**

- Runtime: Node.js 22 LTS. Package manager: pnpm 9.
- API: Express 4 + `serverless-http` on AWS Lambda (Node 22, 1024MB, 29s timeout) behind API Gateway HTTP API.
- Admin: Next.js static export (`output: 'export'`) on AWS Amplify Hosting.
- Database: PostgreSQL 16 (local Docker in dev, Neon in preview/prod). ORM: Drizzle.
- Media: Cloudinary SaaS via Storage Provider Interface; signed direct uploads; server signs only.
- Auth: Better Auth (see ADR-008).
- Async work: EventBridge `rate(1 minute)` → worker Lambda (webhooks + scheduled publishes).

**Deployment rules:**

- One deploy = one project (D2). Same artifact runs locally, on Lambda, and in CI.
- Migrations run as a blocking CI job (`drizzle-kit migrate`) before traffic; never inside handler boot.
- Lambda outside VPC. No provisioned concurrency in MVP.
- Domains: `api.<parent>` (API Gateway custom domain), `admin.<parent>` (Amplify), cookies on `.<parent>`.

**Rate limiting:** `lambda` preset (auth 5/min/IP, public 100/min/IP, publish 30/min/user). Configured via `RATE_LIMIT_PRESET` env var.

## Development Workflow

- **Branch strategy:** PR → `develop` (preview env) → `main` (prod). Feature branches from `develop`.
- **CI gates (every PR):** lint, typecheck, arch boundaries, unit tests, integration tests (Postgres), contract tests (OpenAPI + client), audit (npm audit high = fail, secret scan).
- **Code review:** all changes via PR with at least one approval. Constitution compliance is a review checklist item.
- **Spec-driven development:** features are specified via Spec Kit (`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`), with `/speckit-clarify` to resolve underspecified areas.
- **Quality:** `/code-review` between implementation waves; `security-scanner` before merge for auth/payment/content paths.

## Governance

This constitution supersedes all other practices. All PRs and reviews MUST verify compliance with these principles.

**Amendment procedure:**
1. Propose change via PR with rationale and impact analysis.
2. Update version per semantic versioning (below).
3. Update dependent templates and docs if affected.
4. Obtain maintainer approval before merge.

**Versioning policy:**
- MAJOR: backward-incompatible governance or principle removals/redefinitions.
- MINOR: new principle or section added, or materially expanded guidance.
- PATCH: clarifications, wording, typo fixes, non-semantic refinements.

**Compliance review:**
- Every PR review MUST check constitution compliance.
- Complexity beyond these rules MUST be justified in the PR description.
- Use `docs/` (PRD, architecture, database, deployment, spike) for runtime development guidance.
