## 2. Password Hashing Strategy (FINAL)

**Decision: accept Better Auth's built-in scrypt default for MVP. Argon2id is a documented post-MVP upgrade via custom `hash`/`verify`, not MVP work.**

What was verified:

- Default is `scrypt` (Node.js native, no external dependencies). Official rationale: OWASP recommends scrypt where Argon2id is unavailable, and scrypt ships natively in Node.js.
- Official docs state: "Better Auth uses `scrypt` to hash passwords."
- Custom algorithms are explicitly supported: pass `password: { hash, verify }` in the `emailAndPassword` configuration. The documented Argon2id example uses `@node-rs/argon2` with `memoryCost: 65536 (64 MiB), timeCost: 3, parallelism: 4, algorithm: Argon2id`.
- A third-party claim that Argon2id is the default was found and rejected — official docs say scrypt.

Final strategy:

1. MVP: Better Auth default scrypt. Zero custom crypto code, zero new dependency, OWASP-acceptable.
2. Upgrade path (post-MVP, no schema change): supply custom Argon2id `hash`/`verify` with the documented parameters; existing scrypt hashes remain verifiable during a dual-verify transition window (verify-then-rehash-on-login), then scrypt support retired.
3. FR-024 is updated accordingly: "passwords hashed with Better Auth scrypt default; Argon2id upgrade reserved; never plaintext/MD5/SHA1-only."
4. MUST-CONFIRM-IN-CODE: exact `emailAndPassword.password` option key names against the installed better-auth version (`npx auth@latest --version` + typecheck), since option nesting has shifted between minor versions.

## 3. Session-Store Schema (FINAL)

**Decision: Better Auth owns four tables (`user, session, account, verification`), generated by its CLI, extended for Peggy via `additionalFields`. Peggy never hand-writes these tables.**

What was verified:

- Adapter package is `@better-auth/drizzle-adapter` (do not import from `better-auth/adapters/drizzle`), configured as `drizzleAdapter(db, { provider: "pg" })` over a Drizzle `node-postgres` instance.
- Core tables: `user, session, account, verification` (singular by default; `usePlural: true` maps to plural; `schemaName` option supports a Postgres namespace such as `auth`).
- Session row shape: `id TEXT PK, userId FK → user (cascade), token TEXT UNIQUE, expiresAt, ipAddress, userAgent, createdAt, updatedAt`.
- Account row carries `providerId + accountId` with `UNIQUE(providerId, accountId)`; verification row carries `identifier/value/expiresAt` (OTP, email verification, password reset).
- ID interop with Peggy's UUIDv7 `users.id`: set `advanced: { database: { generateId: false } }` so Postgres generates UUIDs; `session.id/account.id/verification.id` stay `text` PKs internally while `userId` FKs match `uuid`. Verified pattern from official troubleshooting guidance.
- Schema generation: `npx @better-auth/cli generate --adapter drizzle`, then `drizzle-kit generate/migrate`. The generated output is the source of truth — Peggy migrations include it verbatim, never retyped.
- Session expiry defaults: `expiresIn` 7 days, `updateAge` 24h (rolling refresh), `freshAge` 1 day for sensitive actions. Cookie cache (`cookieCache: { enabled, maxAge ~5 min, strategy "jwe" }`) keeps a short-lived encrypted session cookie to avoid a DB read per request.

Final schema decisions for Peggy:

1. Namespace: default (no custom `schemaName`) for MVP to keep Drizzle relations and joins simple; revisit `auth` schema only if table-name collisions with plugins are measured.
2. Peggy's `users` table (§5 of DB doc) IS the Better Auth `user` table: same table, extended via Better Auth `additionalFields` (`displayName, avatarAssetId, isActive, isSuperAdmin`). One identity table, no sync jobs, no drift. MUST-CONFIRM-IN-CODE: `additionalFields` key names and migration output for the installed version.
3. Peggy's `sessions` table (§8 of DB doc) IS the Better Auth `session` table plus Peggy columns `revokedAt` (explicit logout) and reliance on built-in `ipAddress/userAgent`. Sweeper deletes expired rows; revocation sets `revokedAt` with audit tombstone.
4. Session lifetimes MVP: `expiresIn` 7 days admin sessions, `updateAge` 24h, `cookieCache` enabled at 5-min `maxAge` with `jwe` strategy. Rationale: cookieCache is what makes DB-backed sessions affordable on Lambda (hot requests skip the session SELECT).
5. `account`/`verification` tables accepted as-generated; password-reset and email-verification flows use them with single-use expiring tokens (SR-10).

## 4. PostgreSQL Compatibility (FINAL)

- Local dev: container Postgres 16 + `PgPoolAdapter` — matches every official example (`drizzle(pool)`), zero risk.
- Prod/preview on Neon: `NeonHttpAdapter` (fetch-based) is Peggy's choice for content queries. Better Auth's Drizzle adapter receives a Drizzle instance; whether that instance can be Neon-HTTP-backed is the single MUST-CONFIRM-IN-CODE item: boot-test `drizzleAdapter(drizzleNeonHttp(...), { provider: "pg" })` and run sign-in + session-read. If it fails, auth routes use a small `pg` pool (or pooled Neon endpoint) while content traffic stays on HTTP — adapter selection is per-route-group, no domain change.
- Extensions used by auth tables: none beyond standard types (`text/uuid/timestamp`). No `citext` on auth-owned columns (keep generated output verbatim); Peggy's `CITEXT` email uniqueness lives in service-level checks plus a functional unique index if needed, not by altering generated columns.
- `pgcrypto` not required for auth (hashing is app-side scrypt).

## 5. Lambda / Serverless Compatibility (FINAL)

What was verified:

- The Express-on-Lambda pattern (`serverless-http` wrapping the app, API Gateway → Lambda → Express → Better Auth → Postgres) is attested by a production template (`better-auth-serverless`: Express + `serverless-http` + Better Auth + Postgres on Lambda with a JWT authorizer).
- Express mounting rule: `app.all("/api/auth/*", toNodeHandler(auth))` placed BEFORE `express.json()` (the handler consumes the raw body itself); CORS middleware before the auth handler; Express v5 requires `{*any}`-style wildcard.
- Session reads are the hot path: DB-backed sessions mean one SELECT per unauthenticated-cache-miss request. Mitigations finalized: `cookieCache` (5-min JWE) absorbs hot reads; `updateAge` 24h bounds refresh writes; `lastSeen` touches stay async/non-blocking.

Serverless rules locked into the blueprint:

1. No in-memory session state anywhere; every instance reads Postgres (or cookieCache).
2. Auth routes share the same `serverless-http(createApp())` handler — no separate auth service in MVP.
3. Neon scale-to-zero affects auth latency like any query; budget covered by the documented cold-start allowance, and cookieCache hides it for warm sessions.
4. Rate limiting on auth routes is per-target (OQ-03), not global — brute-force protection must survive stateless scale-out, so counters live in Postgres (or future KV), never in process memory.

## 6. Multi-Tenant Session Handling (FINAL — DEFERRED BY DESIGN)

What was verified:

- Better Auth ships a first-class `organization` plugin: `organization/member/invitation` tables, `session.activeOrganizationId`, per-org roles, org switcher semantics, one `member` row per (user, org).
- This is exactly the construct Peggy would adopt IF it ever becomes multi-tenant SaaS.

Decision: **do not install the organization plugin in MVP.** D2 fixes one deploy = one project, so there is exactly one tenant per database and sessions need no tenant discriminator. Installing org tables now would add unused joins, unused admin surface, and migration weight for zero MVP benefit. The blueprint records the adoption path: enable the organization plugin + `activeOrganizationId` scoping + per-org RBAC namespaces when multi-project is approved, as a minor-version migration, not a rewrite. No `tenant_id` columns are added to any MVP table.
